# 04. arm64 向けの準備

手元(WSL)は x86_64、Web Functions の実行環境は arm64 です。
このステップでは、デプロイ先の arm64 でも動く依存パッケージが standalone 出力に入るようにします。

やること:

1. CPU に依存するファイルを確認する
2. pnpm に arm64 用のパッケージもインストールさせる
3. ビルドして、arm64 用のファイルが入ったことを確認する

## 1. CPU に依存するファイルを確認する

JavaScript は CPU に関係なく動きます。問題になるのは、C/C++ などで書かれ、CPU ごとにコンパイルされたバイナリ(拡張子 `.node`)です。

```bash
find .next/standalone -name "*.node"
```

03 のビルド結果では、見つかったのは次の 1 つだけでした。

```text
.next/standalone/node_modules/.pnpm/@img+sharp-linux-x64@0.35.5/node_modules/@img/sharp-linux-x64/lib/sharp-linux-x64-0.35.5.node
```

これは画像処理ライブラリ `sharp` の **x86_64 用**バイナリです。arm64 の実行環境では読み込めません。

### `sharp` はいつ使われるか

Next.js は、`next/image` で表示する画像をアクセス時に縮小・変換して配信します(画像最適化)。この処理に `sharp` を使います。

- `sharp` は、画像最適化を実際に行うときに初めて読み込まれます(`node_modules/next/dist/server/image-optimizer/transform.js` の `getSharp()`)。そのため、x86_64 用しかなくてもサーバー自体は起動します。
- SVG 画像は最適化されません(`src` が `.svg` で終わると自動でスキップされます)。今のトップページの画像は SVG だけなので、現時点では `sharp` は呼ばれません。

つまり今すぐ困るわけではありません。ただ、PNG や JPEG を表示した途端に本番だけで失敗する状態です。デプロイ先に合わせておきます。

## 2. arm64 用のパッケージもインストールする

### しくみ

`sharp` のように CPU ごとにバイナリが分かれるパッケージは、CPU ごとに別パッケージ(`@img/sharp-linux-x64`、`@img/sharp-linux-arm64` など)として配布されています。
pnpm は通常、**手元のマシンに合うものだけ**をインストールします。`supportedArchitectures` 設定を使うと、ほかの CPU 用もインストールさせられます。

CPU ごとのファイルが選ばれるのは `pnpm install` の時点です。`next build` は、インストール済みのものから必要な分をコピーするだけです。

### 設定する

`pnpm-workspace.yaml` に次を追加します。

```yaml
allowBuilds:
  sharp: false
  unrs-resolver: false

supportedArchitectures:
  os: [current, linux]
  cpu: [current, arm64]
  libc: [current, glibc]
```

| 項目 | 意味 |
|---|---|
| `current` | 手元のマシン(Linux / x86_64 / glibc)。**必ず残す** |
| `linux` / `arm64` | デプロイ先の OS と CPU |
| `glibc` | デプロイ先の C ライブラリの種類。Linux には glibc 系と musl 系(Alpine など)があり、パッケージが分かれている |

`current` を外してはいけない理由は 2 つあります。

- `next build` 自体が x86_64 用のネイティブバイナリ(`@next/swc-linux-x64-gnu`)を使っているため、外すと手元でビルドできなくなる
- 手元で `server.js` を動かすときは、x86_64 用の `sharp` が使われる

`sharp` は実行時に自分の CPU に合うバイナリを選んで読み込むので、両方入っていても問題ありません。

> デプロイ先が glibc 系であることは、AWS のドキュメントでまだ確認できていません。Lambda の Node.js ランタイムは Amazon Linux(glibc 系)なので、同じだと想定しています。もし違えば、画像最適化を使ったときに `sharp` の読み込みエラーで分かります。

### インストールする

`node_modules` を消してから入れ直します。

```bash
rm -rf node_modules && pnpm install
```

> **単に `pnpm install` を実行しても入りません。** pnpm は `package.json` とロックファイルに変化がなければ、インストールを丸ごと省略します(`Already up to date` と表示されます)。`supportedArchitectures` の変更は、この判定に含まれないようです。
> `pnpm upgrade` でも入りますが、`package.json` のバージョン指定(`^4` → `^4.3.3` など)まで書き換えられるので、この目的には向きません。

arm64 用のパッケージが入ったか確認します。

```bash
ls node_modules/.pnpm | grep "@img+sharp"
```

次のように、`linux-x64` と `linux-arm64` の両方があれば成功です。

```text
@img+sharp-libvips-linux-arm64@1.3.4
@img+sharp-libvips-linux-x64@1.3.4
@img+sharp-linux-arm64@0.35.5
@img+sharp-linux-x64@0.35.5
```

(バージョン番号は異なる場合があります。`sharp-libvips-*` は `sharp` が内部で使う画像処理ライブラリ本体です。)

`pnpm-lock.yaml` は変わりません。CPU ごとのパッケージは、もともとロックファイルに候補として全部書かれていて、どれを実際に入れるかを `supportedArchitectures` が決めているためです。

`@next/swc-linux-arm64-gnu`(arm64 でビルドするときに使う Next.js のコンパイラ)もダウンロードされます。手元では使いませんし、standalone 出力にも入らないので、気にしなくて大丈夫です。

## 3. ビルドして確認する

```bash
pnpm build
find .next/standalone -name "*.node"
```

x86_64 用と arm64 用の 2 つが表示されれば成功です。

```text
.../@img/sharp-linux-x64/lib/sharp-linux-x64-0.35.5.node
.../@img/sharp-linux-arm64/lib/sharp-linux-arm64-0.35.5.node
```

`sharp` のソース(`dist/sharp.cjs`)は、CPU ごとのバイナリをすべて固定の名前で `require` しています。そのため、インストールさえされていれば Next.js のトレースが自動で拾う見込みです。
**arm64 用が表示されない場合は**、トレースが拾えていません。結果を共有してください。`next.config.ts` の `outputFileTracingIncludes` で明示的に含める方法を検討します。

画像処理ライブラリ本体も入ったか確認します。

```bash
ls .next/standalone/node_modules/.pnpm | grep "@img+sharp"
```

最後に、サイズとローカルでの起動を確認します。

```bash
du -sh .next/standalone/
HOSTNAME=0.0.0.0 PORT=3000 node .next/standalone/server.js
```

サイズは 03 の 41 MB から、arm64 用の分だけ増えます。ブラウザで http://localhost:3000 が 03 と同じように表示されれば完了です。

> この時点で確認できるのは「arm64 用のファイルがパッケージに入った」ことまでです。本番で実際に動くかは、PNG などの画像を表示して初めて分かります。必要なら 06 以降で試します。

- [ ] `.next/standalone` に x86_64 用と arm64 用の `.node` ファイルがある
